# Supabase — schema and migrations

This folder keeps the database definition as code (SQL), so it is versioned together with the app.

It is empty for now — the table schema (tournaments, players, matches, results) will be added once the
business requirements are settled (Americano/Mexicano rules, how scoring is calculated).

## How to hook it up (one-time)

1. Install the Supabase CLI: `npm install -g supabase`
2. Log in: `supabase login`
3. Link this folder to the Supabase project you create on supabase.com:
   `supabase link --project-ref YOUR_PROJECT_REF`
4. Create new migrations with: `supabase migration new migration_name`
   — this creates an SQL file in `supabase/migrations/` where you describe the table changes.
5. Push the migrations to the live database: `supabase db push`

This way the whole database structure lives in Git, not just "in your head" or in the dashboard.

## Do not run `supabase config push`

Only migrations are pushed to the live project, with `supabase db push`.

`config.toml` was generated by `supabase init` and its `[auth]` section is boilerplate —
`site_url` points at `127.0.0.1:3000`, alongside default JWT expiry, password rules and
rate limits. None of it reflects the live project. `config push` would overwrite the real
auth configuration with those defaults, which at minimum breaks magic-link sign-in by
resetting the redirect allowlist.

Auth settings are managed in the dashboard: **Authentication → URL Configuration**. After
deploying, Site URL and Redirect URLs must include the production domain, or the sign-in
link refuses to redirect back.

## Recreating a view

Dropping and recreating a view in `public` re-acquires Supabase's default privileges for
`anon` and `authenticated` — the revokes from the initial schema do **not** survive. Any
migration that recreates a view must re-state its grants, and the push should be followed by

```sql
select grantee, privilege_type from information_schema.role_table_grants
where table_name = '<view>';
```

`20260818040000` exists because `20260818030000` missed this.

## Round notifications (ADR-0004)

Push needs four things set up once per project, outside the migrations:

1. A VAPID key pair: `npx web-push generate-vapid-keys`. The public key goes into
   `VITE_VAPID_PUBLIC_KEY` (`.env` and the hosting provider's environment); without it
   the public page hides the notifications button.
2. Edge Function secrets, then deploy:
   ```bash
   supabase secrets set VAPID_PUBLIC_KEY=… VAPID_PRIVATE_KEY=… \
     VAPID_SUBJECT=mailto:you@example.com NOTIFY_ROUND_SECRET=<random string>
   supabase functions deploy notify-round
   ```
   `config.toml` sets `verify_jwt = false` for this function: the caller is the database,
   which has no JWT. The function checks `NOTIFY_ROUND_SECRET` instead.
3. Vault secrets the trigger reads, in the SQL editor:
   ```sql
   select vault.create_secret('https://<ref>.supabase.co/functions/v1/notify-round', 'notify_round_url');
   select vault.create_secret('<same random string>', 'notify_round_secret');
   ```
4. `supabase db push` for `20260821000000_round_push_notifications.sql`.

Until both vault secrets exist the trigger does nothing, so a round is never blocked by
push being half-configured. Delivery results land in `net._http_response` and in the
function's logs.
